# Languages (i18n)

Gantry's interface is available in English (the default and source language)
and Bahasa Indonesia. Users choose a language in the user menu (Language) or on
the Account page. The sign-in screens have a language select too.

## How it works

- **Choice:** the `gantry-locale` cookie, set by the `setLocale` Server Action
  (`lib/i18n/actions.ts`). It is remembered per browser for a year. Without
  the cookie the interface is English.
- **Server rendering:** `getLocale()` / `getI18n()` (`lib/i18n/server.ts`) read
  the cookie. Server Components, Server Actions and Route Handlers call
  `getI18n()`; client components call `useI18n()` (`lib/i18n/client.tsx`),
  which gets the language from the nearest `<LocaleScope>`
  (`components/i18n/locale-scope.tsx`). Every page, the header and the
  sidebar sections are wrapped in one, inside a `<Suspense>` boundary (the
  app uses Cache Components, so reading a cookie must happen inside one).
  The server therefore renders the chosen language directly: there is no
  flash of English.
- **`<html lang>`:** the root layout is static, so a small inline script in
  `app/layout.tsx` sets `lang` from the cookie before the first paint (as the
  Next.js docs recommend for attributes on `<html>`).
- **No language routes:** URLs stay the same in every language (no `/id/...`
  prefix). Gantry is a signed-in admin tool, not a public site, so the
  per-path routing of the Next.js internationalization guide would only
  break bookmarks, webhooks and API paths. The dictionaries follow that
  guide: plain typed objects, no i18n library.

## Dictionaries

`lib/i18n/dictionaries/<locale>/<namespace>.ts`, one namespace per area
(`common`, `nav`, `containers`, `stacks`, ...), combined in
`lib/i18n/dictionaries/<locale>/index.ts`.

- English (`en/`) is the source of truth. Its objects are `as const`, so the
  type `Dictionary` (`lib/i18n/dictionaries/types.ts`) has exactly its keys.
  Every other language is typed `Dictionary["<namespace>"]`: a missing or
  misspelled key is a type error.
- Placeholders are `{name}`: `i18n.format(t.containers.removeTitle, { name })`.
  `format()` checks the placeholder names against the English text at
  compile time.
- Counts use `{ one, other }` objects and `i18n.plural(entry, count)`, which
  picks the form with `Intl.PluralRules` (Indonesian always uses `other`).
- Text with links or code inside uses `i18n.rich(template, { link: <Link…/> })`.
- Dates, relative times, numbers and byte sizes: `i18n.formatDate()`,
  `i18n.timeAgo()`, `i18n.formatNumber()`, `i18n.formatBytes()`.
  English keeps the formats Gantry always used.
- `tests/unit/i18n.test.ts` checks that every language has exactly the
  English keys, the same placeholders in each message, and no empty message.

Messages produced by library code that also runs outside a request (for
example `lib/messages.ts`) stay English at the source and are translated
where they are shown, through `lib/i18n/known-messages.ts`. Errors that come
from Docker, Kubernetes or Git themselves are shown as they are.

## Style for Indonesian

Write the way Indonesian sysadmins talk: natural, short, "Anda" for the
reader. Keep the terms people actually use in English: container, image,
volume, network, stack, deploy, pull, push, registry, environment, log,
port, Helm, and every Docker or Kubernetes object name (Pod, Service,
ConfigMap...). Translate the surrounding words (Hapus, Simpan, Batal,
Jalankan, Hentikan...).

## Adding a language

1. Add its code to `LOCALES`, its own name to `LOCALE_NAMES` and its Intl
   tags to `INTL_LOCALES` in `lib/i18n/config.ts`.
2. Copy `lib/i18n/dictionaries/id/` to `lib/i18n/dictionaries/<code>/`,
   rename the export in `index.ts`, and translate every message. Keep the
   `{placeholders}` exactly as in English.
3. Register it in `lib/i18n/dictionaries/index.ts`.
4. Run `pnpm exec tsc --noEmit` (missing keys) and
   `pnpm test tests/unit/i18n.test.ts` (keys and placeholders).

The switcher lists every language in `LOCALES` automatically.
